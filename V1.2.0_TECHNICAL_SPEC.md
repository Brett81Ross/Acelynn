# Acelynn Pro Studio™ — v1.2.0 Technical Build Specification

**Status:** Canonical implementation candidate — repo-reconciled, pending final red-team/build green-light  
**Product name:** Acelynn Pro Studio™  
**Current production baseline:** Acelynn Pro™ v1.1.2  
**Core rule:** Audio remains on-device. No source audio is persisted to IndexedDB or uploaded.  
**Deployment rule:** Vercel Git deployment stays locked until the complete release passes QA and the CEO explicitly approves deployment.

## 1. Verified current repo baseline

The current app is a static browser/PWA foundation. `app-base.html` and `index.html` are currently identical. Production `/` and `/index.html` are rewritten by Vercel to `api/demo-shell.js`, which fetches `app-base.html`, injects the version/demo help script, and returns the application shell.

The current snapshot implementation stores at most 12 entries in `localStorage` under `acelynn-snapshots`. Each legacy snapshot contains only:

- localized display time text
- listening-profile display name
- legacy Mix Health score
- dominant/focus band label
- five analyser byte-energy averages

Legacy snapshots **do not store** source type (file vs microphone), selected analysis perspective, peak/RMS values, true band dB values, spectral features, confidence factors, or the coaching text shown at capture time.

The current app actively registers `./sw.js`. The worker caches `index.html`, manifest, logo, and demo-help assets. v1.2.0 will remove this service-worker architecture and include a one-time cleanup path so previously installed workers/caches are actually unregistered instead of merely orphaned.

## 2. v1.2.0 product scope

v1.2.0 establishes the data and workflow foundation for the six long-term Acelynn systems:

1. Acelynn Translation Matrix™ — schema/future hooks only in v1.2.0
2. Mix Evolution Matrix™ — first functional implementation
3. Confidence-Aware Mix Health™ — first functional implementation
4. Private Reference Intelligence™ — first functional implementation
5. Explainable Coaching Matrix™ — deterministic foundation retained and structured
6. Translation Memory™ — schema/training-data foundation only; no learning model yet

No on-device ML model, cloud audio processing, room-calibration workflow, stem separation, or cloud sync ships in v1.2.0.

## 3. Static-app module architecture

The application remains browser-native with no production bundler requirement. v1.2.0 should split the current single large inline script into small same-origin ES modules:

- `js/app.js` — UI orchestration and lifecycle
- `js/db.js` — IndexedDB open/CRUD/transactions
- `js/migration.js` — legacy snapshot dry-run/import
- `js/analysis.js` — frame aggregation and spectral feature extraction
- `js/scoring.js` — profile targets, perspective weighting, Mix Health
- `js/confidence.js` — source-specific confidence calculation
- `js/coaching.js` — deterministic Explainable Coaching Matrix rules
- `js/references.js` — local reference fingerprints/comparison
- `js/export.js` — JSON/CSV export
- `js/storage.js` — quota/footprint/persistence health

`app-base.html` remains the production source shell. `index.html` remains a static fallback copy and must be kept text-identical by QA. `api/demo-shell.js` remains the production wrapper in v1.2.0 to avoid an unrelated routing rewrite during this release.

A small app metadata file should become the version/name source for QA and shell surfaces rather than adding more independent hard-coded version strings.

## 4. IndexedDB schema

**Database:** `AcelynnProStudioDB`  
**IndexedDB version:** `1`

### `meta`

Key path: `key`

Used for schema metadata, migration state, storage preferences, and feature-definition versions.

Example keys:

- `schema`
- `legacyMigration`
- `storagePreferences`
- `featureDefinitions`

### `projects`

```ts
interface ProjectRecord {
  id: string;               // UUID
  name: string;
  createdAt: number;        // epoch ms
  updatedAt: number;
  metadata: {
    artist?: string;
    genre?: string;
    bpm?: number;
    notes?: string;
  };
}
```

Indexes:

- `byName` -> `name`
- `byCreatedAt` -> `createdAt`
- `byUpdatedAt` -> `updatedAt`

### `songs`

```ts
interface SongRecord {
  id: string;
  projectId: string;
  name: string;
  createdAt: number;
  updatedAt: number;
  metadata: {
    durationSec?: number;
    sampleRateHz?: number;
    fileFingerprint?: string; // optional metadata fingerprint, not source audio
  };
}
```

Indexes:

- `byProject` -> `projectId`
- `byProjectCreated` -> `[projectId, createdAt]`
- `byName` -> `name`

IndexedDB does not enforce foreign keys; all project/song/version cascades are enforced by the CRUD layer inside explicit transactions.

### `versions`

This is the primary observation store.

```ts
interface VersionRecord {
  id: string;
  songId: string;
  parentVersionId: string | null;
  versionLabel: string;
  createdAt: number;
  importedAt?: number;

  origin: 'native-v1.2' | 'legacy-v1.1';
  featureSchemaVersion: number;

  sourceType: 'file' | 'live-mic' | 'legacy-unknown';
  sourceMetadata: {
    fileName?: string;
    fileSize?: number;
    sampleRateHz?: number;
    micDeviceLabel?: string;
    micSettings?: Record<string, unknown>;
    processingRequestedOff?: boolean;
    processingConfirmedOff?: boolean;
  };

  perspective: 'full-mix' | 'room-speaker' | 'detail-harshness' | null;
  listeningProfile: 'balanced' | 'bass' | 'acoustic' | 'vocal' | null;

  bands: {
    sub: BandObservation;
    bass: BandObservation;
    mids: BandObservation;
    presence: BandObservation;
    air: BandObservation;
  };

  levels: {
    peakDbfs: number | null;
    rmsDbfs: number | null;
    crestDb: number | null;
  };

  dominantFrequencyArea: 'sub' | 'bass' | 'mids' | 'presence' | 'air' | null;

  spectralFeatures: SpectralFeatures | null;

  mixHealth: {
    raw: number | null;
    perspectiveWeighted: number | null;
    targetProfileMatch: number | null;
  };

  confidence: ConfidenceRecord;

  coachingFindings: CoachingFinding[];

  referenceDeltas: ReferenceDelta[];

  roomSignatureId: string | null; // reserved only; no v1.2 room-signature workflow
  roomConfidence: number | null;  // reserved only

  userNotes?: string;

  legacy?: {
    legacyTimeLabel?: string;
    legacyOrder?: number;
    originalSnapshot?: unknown;
  };
}

interface BandObservation {
  linearPower: number | null;
  percentOfObservedPower: number | null; // 0..100
  relativeDb: number | null;             // dB relative to total observed spectral power
  legacyByteEnergy?: number;             // populated only for migrated v1.1 snapshots
}

interface SpectralFeatures {
  definition: 'log16-v1';
  spectralCentroidHz: number;
  spectralFlatness: number;        // 0..1
  spectralRolloff85Hz: number;
  coarseSpectrum: number[];        // exactly 16 normalized power-share bins, sum approximately 1
  bandSpectralContrastDb: {
    sub: number;
    bass: number;
    mids: number;
    presence: number;
    air: number;
  };
}
```

Indexes:

- `bySong` -> `songId`
- `bySongCreated` -> `[songId, createdAt]`
- `byParent` -> `parentVersionId`
- `byCreatedAt` -> `createdAt`
- `bySourceType` -> `sourceType`
- `byPerspective` -> `perspective`

Do not add indexes solely because a field exists. High-cardinality score/confidence filtering can be done in-memory per song in v1.2.0; this keeps writes and schema simpler.

### `references`

No audio bytes are persisted.

```ts
interface ReferenceRecord {
  id: string;
  scope: 'global' | 'song';
  songId?: string;
  name: string;
  createdAt: number;

  bands: VersionRecord['bands'];
  levels: VersionRecord['levels'];
  dominantFrequencyArea: VersionRecord['dominantFrequencyArea'];
  spectralFeatures: SpectralFeatures;

  metadata: {
    fileFingerprint?: string;
    durationSec: number;
    sampleRateHz: number;
  };
}
```

Indexes:

- `byScope` -> `scope`
- `bySong` -> `songId`
- `byCreatedAt` -> `createdAt`
- `byName` -> `name`

A separate `scope` field is required because IndexedDB indexes do not provide a reliable query mechanism for `null` as a synthetic global-scope key.

### Room-signature storage

No `roomSignatures` object store is created in DB v1. The version record reserves the future relationship fields only. When the Advanced Beta calibration workflow is designed, IndexedDB will receive an explicit versioned migration and its own tested store. Creating an unused store now would give a false impression that the feature is implemented and would not eliminate the need for future migrations anyway.

## 5. Spectral feature extraction — future-ML ready without ML

The current v1.1 app uses `getByteFrequencyData()` for display and five-band averages. v1.2.0 keeps byte data available for the visualization but must use `getFloatFrequencyData()` converted from dB to linear power for stored spectral features.

The stored feature vector is intentionally compact:

- five relative band-power observations
- global peak/RMS/crest
- spectral centroid
- spectral flatness
- 85% spectral rolloff
- 16 logarithmically spaced coarse power bins from 20 Hz to the available upper bound (up to 20 kHz)
- five per-band spectral-contrast values

The spec intentionally does **not** call the per-band feature “crest factor.” True per-band crest factor requires a time-domain filter-bank or equivalent band-limited peak/RMS pipeline. v1.2.0 instead stores spectral contrast that can be calculated honestly from FFT power distribution at low cost.

Feature calculations must be aggregated across the analysis window rather than freezing a single animation frame. Save captures the accumulated observation state since the current analysis started/reset.

No raw PCM, decoded file buffer, FFT frame history, spectrogram image, or audio Blob is persisted.

## 6. Mix Health and perspective weighting

Current profile IDs remain stable for compatibility:

- `balanced`
- `bass`
- `acoustic`
- `vocal`

The existing display labels remain user-facing.

v1.2.0 replaces the current ad-hoc mode penalties with explicit normalized band weights.

Initial deterministic weights:

| Perspective | Sub | Bass | Mids | Presence | Air |
| --- | ---: | ---: | ---: | ---: | ---: |
| Full mix | 1.00 | 1.00 | 1.00 | 1.00 | 1.00 |
| Room / speaker | 1.25 | 1.20 | 1.00 | 0.85 | 0.70 |
| Detail / harshness | 0.65 | 0.80 | 1.05 | 1.35 | 1.25 |

Weights are normalized before calculating the weighted mean absolute profile error so a perspective does not receive a systematic scoring advantage merely because its weight sum differs.

`mixHealth.raw` is the equal-weight profile score. `mixHealth.perspectiveWeighted` is the selected-perspective score.

**Confidence does not multiply or overwrite Mix Health.** Measurement quality and mix balance are different facts. Confidence mathematically controls claim strength/coaching priority and later Translation Matrix evidence weighting.

## 7. Confidence-Aware Mix Health

Confidence is source-specific and based only on measurable properties. It must never imply laboratory calibration.

### Shared factors

- analysis duration/coverage
- signal adequacy
- clipping incidence
- analysis continuity / dropped-frame gaps

### File-analysis factors

File analysis is not penalized for musical dynamics or a supposed “noise floor.” Dynamic range is content, not measurement instability. File confidence weights source integrity/coverage and continuity more heavily.

### Live-mic factors

Live-mic confidence additionally considers whether requested browser capture processing (echo cancellation, noise suppression, AGC) is confirmed disabled by `MediaStreamTrack.getSettings()` where exposed. If the browser does not report those settings, Acelynn records uncertainty instead of claiming compensation.

Observed low-level percentile may be stored as an **observed signal floor**, but it is not labeled a calibrated ambient noise floor unless a future dedicated measurement procedure provides one.

### Confidence bands

- 85–100: High confidence
- 65–84: Moderate confidence
- 45–64: Low confidence
- below 45: Insufficient/weak evidence
- `null`: Unrated legacy observation

`claimStrengthFactor = overall / 100` for native records. Deterministic coaching uses confidence to rank and phrase findings, not to falsify the underlying Mix Health number.

Example language:

- High: “Presence buildup is consistently above this target.”
- Moderate: “Presence appears elevated; verify around 2–6 kHz.”
- Low: “This capture suggests elevated presence, but measurement confidence is low.”

## 8. Explainable Coaching Matrix™ foundation

Every new native v1.2 finding stores a stable rule/suggestion ID and structured evidence.

```ts
interface CoachingFinding {
  id: string;
  ruleId: string;
  origin: 'deterministic';
  category: 'sub-bass' | 'bass' | 'mids' | 'presence' | 'air' | 'balance';
  severity: 'low' | 'medium' | 'high';
  confidenceAtCapture: number;
  detectedValue: number | null;
  targetValue: number | null;
  delta: number | null;
  deltaUnit: 'profile-points' | 'relative-db' | null;
  description: string;
  listenFor: string;
  inspectionAction: string;
}
```

Advice should diagnose and suggest inspection before prescribing blind EQ moves.

## 9. Private Reference Intelligence™ foundation

Reference audio is selected by the user, decoded/analyzed locally, fingerprinted into the same v1.2 feature definition, and released after analysis. Only derived statistics and metadata persist.

A comparison stores:

```ts
interface ReferenceDelta {
  referenceId: string;
  referenceNameAtAnalysis: string;
  bandDeltaDb: {
    sub: number;
    bass: number;
    mids: number;
    presence: number;
    air: number;
  };
  overallMatch: number;
  featureSchemaVersion: number;
}
```

Historical deltas remain meaningful if a reference is later deleted because the reference name and calculated deltas are snapshotted into the version record.

## 10. Mix Evolution Matrix™ foundation

Users can select any two native versions of the same song.

Comparison output includes:

- five-band relative-dB deltas
- raw Mix Health delta
- perspective-weighted score delta when the same perspective is used
- confidence delta
- previously detected deterministic findings that improved/resolved
- persistent findings
- newly introduced findings
- correction-side-effect warning when one material improvement coincides with a newly significant problem elsewhere

Legacy imported records can appear in the timeline but must be visibly labeled **Legacy / limited data**. Comparisons that require unavailable metrics are disabled or shown as unavailable rather than silently inventing values.

## 11. Legacy snapshot migration

### Mandatory dry-run

On first v1.2 launch:

1. Read and parse `localStorage['acelynn-snapshots']` without modifying it.
2. Validate the array and each recognized field.
3. Show the number of importable snapshots and explain which fields cannot be recovered.
4. User can import or skip.

### Correct legacy mapping

Do **not** assume the legacy source was a file. Do **not** assign a fabricated 70% confidence score. Do **not** claim reconstructed coaching was captured at the original time.

For each imported snapshot:

- `origin = 'legacy-v1.1'`
- `sourceType = 'legacy-unknown'`
- `perspective = null` because v1.1 did not save the selected analysis mode
- map recognized profile display names back to stable profile IDs
- preserve the five legacy analyser byte averages in `legacyByteEnergy`
- derive only relative percentages that are mathematically recoverable from those saved values
- modern band relative-dB values remain `null` unless explicitly derivable under the legacy basis and labeled as such
- global peak/RMS/crest remain `null`
- `spectralFeatures = null`
- preserve the old score as `mixHealth.raw`; `perspectiveWeighted = null`
- `confidence.overall = null` and status is Legacy / unrated
- `coachingFindings = []` unless a future reconstruction is explicitly marked reconstructed; v1.2 import does not fabricate them
- preserve the original localized time label as `legacy.legacyTimeLabel`
- preserve array order as `legacy.legacyOrder`

The old localized label contains no year and is not guaranteed to be parseable across locales. Therefore it is not converted into a fake historical epoch timestamp. Imported records receive an import-order timestamp for deterministic sorting and retain the original label for display.

### Transaction safety

After IndexedDB stores are created, the actual import uses one read/write transaction spanning:

- `projects`
- `songs`
- `versions`
- `meta`

The migration creates:

- Project: `Imported Snapshots`
- Song: `Imported Mixes`

The migration marker is written only if all records commit successfully. If the transaction aborts, no partial migration marker is written.

Legacy `localStorage` data is retained by default after a successful import. Because it is at most 12 tiny records, preservation is safer than destructive cleanup. Settings can later offer **Remove legacy backup** explicitly.

Migrated legacy records are excluded by default from any future ML training/export dataset that requires native v1.2 spectral/confidence features.

## 12. Storage Health Module

Use `navigator.storage.estimate()` where available, with transparent wording that the quota/usage numbers are **browser-origin estimates**, not a precise Acelynn-only database size.

Acelynn also computes an approximate record footprint from serialized IndexedDB records so the UI can distinguish:

- browser-origin storage estimate
- Acelynn structured-record footprint estimate

No fixed “5 KB/version” fallback is presented as fact.

Quota warnings apply only when a usable browser quota is reported:

- 60%: advisory warning
- 80%: strong warning
- 90%: persistent critical warning before saves

When `navigator.storage.persisted()` / `navigator.storage.persist()` is available, Settings may expose a best-effort **Protect local data** action. The UI must state that browser/OS eviction policies can still vary, especially on mobile.

## 13. Service-worker removal

v1.2.0 removes active service-worker registration and deletes the cache-first `sw.js` architecture.

A one-time cleanup path runs on v1.2 startup:

- enumerate same-origin service-worker registrations and unregister Acelynn registrations
- delete cache names beginning with the legacy `acelynn-pro-` prefix
- never register a replacement worker

This cleanup is regression-tested. The manifest remains so the app can continue to support home-screen/standalone installation behavior where the browser permits it.

## 14. Session timeline and export

Timeline is song-centric and displays versions chronologically with filters for:

- perspective
- listening profile
- source type
- confidence band
- native vs legacy origin

JSON export supports:

- one version
- one song with all versions
- one project with all songs/versions

CSV export supports timeline/measurement rows suitable for session notes. Exports contain structured observations only; never audio bytes.

## 15. Acceptance criteria

- **AC-1 Projects/Songs:** create, rename, delete; transactional cascade rules verified.
- **AC-2 Versions:** file/live-mic saves complete native schema; legacy records remain explicitly limited.
- **AC-3 Spectral extraction:** float-frequency power pipeline produces centroid, flatness, rolloff, log-16 spectrum, five spectral-contrast values.
- **AC-4 Aggregation:** saved observations represent the analysis window, not one animation frame.
- **AC-5 Mix Evolution:** compare two versions of one song and show supported deltas/findings changes.
- **AC-6 Perspective scoring:** explicit normalized weights replace the old fixed penalty logic.
- **AC-7 Confidence:** source-specific confidence is stored, displayed, and changes coaching claim strength without rewriting Mix Health.
- **AC-8 References:** local file -> derived fingerprint -> comparison; audio is not persisted.
- **AC-9 Timeline:** project/song/version history with required filters and legacy labels.
- **AC-10 Export:** JSON and CSV exports contain only structured local observations.
- **AC-11 Storage:** transparent quota/footprint display and 60/80/90 warnings when quota is available.
- **AC-12 Migration:** dry-run, transactional import, no fabricated source/confidence/time/coaching fields, legacy backup retained.
- **AC-13 Room signature:** relationship fields reserved, but there is no room calibration UI/workflow in v1.2.0.
- **AC-14 Service worker:** no active registration remains; old registrations/caches are cleaned.
- **AC-15 Privacy:** no source audio is uploaded or persisted.
- **AC-16 Version/branding:** Acelynn Pro Studio™ v1.2.0 surfaces are consistent; central CactusByte demo slug can remain `acelynn-pro` for compatibility.

## 16. QA strategy and browser matrix

### Automated CI — release blocking

The existing Jekyll Docker workflow does not meaningfully validate this browser application and should be replaced by an Acelynn-specific QA workflow during Sprint 1.

Automated QA will cover:

- schema/open/upgrade tests
- migration dry-run and transaction-abort tests
- CRUD/cascade tests
- reference deletion/history behavior
- scoring/confidence deterministic tests
- feature-vector shape/range tests
- JSON/CSV export tests
- service-worker cleanup guard
- app-base/index parity
- version/name consistency
- no audio persistence paths
- browser smoke/e2e via Chromium and WebKit-compatible automation where practical
- Firefox smoke path

### Target browser matrix

| Platform | Browser | Release status |
| --- | --- | --- |
| Android 12+ | Chrome latest | Blocking |
| Android 12+ | Samsung Internet latest | Blocking |
| iOS 16+ | Safari latest available on supported device | Blocking |
| Windows/macOS | Chrome latest | Blocking |
| Windows | Edge latest | Blocking |
| Desktop | Firefox latest | Smoke; blocking for data corruption/core save failure |
| Android | Firefox latest | Smoke; blocking for data corruption/core save failure |

Playwright/WebKit is a useful CI proxy but must not be described as proof that real iOS Safari passed. Likewise Chromium automation is not proof that Samsung Internet passed. Final release notes must distinguish automated proxy coverage from actual-device checks.

No WebGPU/WebNN dependency exists in v1.2.0. Spectral extraction uses Web Audio + CPU/browser primitives, so no unnecessary WASM/WebGPU polyfill architecture is introduced.
